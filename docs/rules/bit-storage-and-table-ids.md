# 位图（Bit）存储规范与策划删表 ID 约束（Python 版）

> 对应根索引 [AGENTS.md](../../AGENTS.md)，与 C++/Go 权威仓 `docs/rules/bit-storage-and-table-ids.md` 保持同一套存档与配表纪律。

## 1. 优先用 bit 存储纯布尔状态

- 玩家针对配置表稳定 ID 的纯布尔状态（完成、已领取、已解锁、引导步骤等）**优先使用紧凑位图存储**（proto 落盘为 `bytes`，第 `i` 位落第 `i // 8` 字节的第 `i % 8` 位，低位在前、末尾全 `0` 字节不写）。
- **禁止直接用配置表 ID 当 bit 下标**，必须通过权威导表器 `(cfg_bit_index) = true` 维护的 `ID -> 紧凑 bit_index` 映射转换。
- 高频轮换的限时活动不塞进永久单调增长的全局位图，应按 `activity_id` / 期次独立存档并支持过期整条清理；声明了 `(cfg_multi) = true` 的可重复主键表不使用位序。
- **领取状态归属**：每个业务系统自己持有位图，位序绑在本系统自己的表，不绑在公共 `Reward` 表上（`Reward` 表只表达发什么物品/货币）。

## 2. 上线后删表 ID 的程序与策划红线

位序映射唯一权威源在 C++/Go 仓 `tools/data_table_exporter/state/mapping/table_index_mapping/<表名小写>_mapping.json`：

- **空位永久保留不回收**：删表行后旧 ID 位序永久占位，新 ID 只从 `max(已分配) + 1` 追加。
- **策划红线**：
  1. **上线后绝不复填已删除/废弃的旧 ID**（否则老玩家历史 `1` 位会静默串味成“已完成/已领过新内容”）；
  2. 有进行中/待领奖老玩家的表优先下架/禁用而非物理删行，物理删行前先与程序确认清理和计数口径；
  3. 严禁手改或删除 `*_mapping.json`；想重置领奖资格必须新建业务 ID。
- **程序红线**：
  1. 严禁手改、删除位序映射文件或对已发布表重建位序；
  2. 遍历存档中“进行中/待领奖”ID 查表时，查不到（`None`）必须安全跳过或做下线清理，不得抛 `KeyError` / `AttributeError` 卡登录；
  3. 统计“当前有效完成数”不得直接对整个位图做 `popcount`（会把已删 ID 历史残留 `1` 位算进去），必须按当前有效表行集合过滤统计；
  4. 灰度/混跑读盘遇到超出当前表位序上限的高位 bit，必须**原样保留完整字节并在存盘时原样写回**，严禁截断丢弃。
